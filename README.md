# KNEO Automation — Website

A 40-page static marketing site for KNEO Automation Pvt. Ltd. — industrial automation,
Industry 4.0 and the MAPP MES/IIoT platform.

No frameworks, no build tooling, no dependencies. Plain HTML, one stylesheet, one script.
Every page is a standalone file that works when opened directly or served from any host.

---

## 1. Running it

**Just double-click `index.html`.** Every page, link and interaction works straight from the
file system — no server needed. The only thing that needs an internet connection is Google
Fonts, and there is a system-font fallback if it is unavailable.

### If you want a real web server

Double-click **`start-server.cmd`**, which opens the site at `http://localhost:8123/`.

> **Keep that window open while you browse.** If you close it, the server stops. Pages
> already on screen keep displaying, but every link will stop working — which looks exactly
> like "the site is broken" when it is only the server that has gone away.

Use the server when testing things that need real HTTP: `sitemap.xml`, `robots.txt`, the 404
page, or showing the site to someone else on your network.

On macOS or Linux, run `perl _tools/serve.pl . 8123` instead.

### Building after an edit

```bash
bash build.sh
```

In VS Code, **Ctrl+Shift+B** runs the same thing — see `.vscode/tasks.json`, which
also has tasks for the preview server and for building then opening the browser.

**One-time setup, worth doing.** The pages load minified copies of the stylesheet and
script — `main.min.css` and `main.min.js` — which are roughly half the size of the
readable originals. Those are produced at build time by two tools that are not
installed by default:

```bash
cd _tools && npm install
```

Without them the build still works and the site is still correct; it just ships the
full-size files instead, and says so:

```
! assets: not minified (cd _tools && npm install) — assets copied as-is
```

`assets/css/main.css` and `assets/js/main.js` remain the source you edit. The `.min`
files are generated — never edit those directly, they are overwritten on every build.

> The tooling lives in `_tools/`, not the project root, deliberately. A `package.json`
> at the root changes how some hosts treat the project: they stop serving it as plain
> static files and start looking for a build to run.

### Building for a different domain

The site URL is a build parameter, not something hardcoded:

```bash
SITE_URL=https://kneo.in bash build.sh
```

That regenerates every canonical tag, `og:url`, `sitemap.xml` and `robots.txt`.

```
/

├── about/index.html               ← served at /about/
├── mapp/index.html                ← served at /mapp/
│   └── mapp-eye/index.html        ← served at /mapp/mapp-eye/
├── services/      (hub + 8 service pages, each its own directory)
├── products/      (hub + 4 Digital Quality 4.0 product pages)
├── industries/    (hub + 6 industry pages)
├── 404.html                       ← a real file; hosts serve it by path
├── .htaccess                      ← Apache config (see §8)
├── sitemap.xml    robots.txt      ← regenerated by the build
│
├── assets/
│   ├── css/main.css               ← the entire design system
│   ├── js/main.js                 ← all site behaviour
│   ├── img/                       ← favicon, hero fallback, social card
│   │   └── logos/                 ← drop brand logos here (see §6)
│   └── video/                     ← optional background video (see §5)
│
├── _source/                       ← EDIT HERE, then run the build
│   ├── partials/
│   │   ├── head.html              ← <head>, meta, JSON-LD, theme bootstrap
│   │   ├── header.html            ← header, mega-menu, mobile drawer
│   │   └── footer.html            ← footer + script tag
│   └── pages/                     ← one file per page (body content only)
│
├── _tools/serve.pl                ← tiny local static server
└── build.sh                       ← assembles _source → root
```

### Why a `_source` folder?

The header and footer appear on all 40 pages. Editing them in one place and rebuilding is
the difference between a two-second change and 40 hand edits that drift out of sync.

The **output is still plain static HTML** — nothing about hosting or deployment depends on
the build. If you would rather stop using it, delete `_source/` and `build.sh` and edit the
root `.html` files directly.

## 3. Editing content

### Change text on one page
Edit the matching file in `_source/pages/`, then run:

```bash
bash build.sh
```

Each source page begins with four metadata lines:

```
@TITLE  Page title | KNEO Automation      ← browser tab + search result title (≤60 chars)
@DESC   Meta description for SEO.         ← search snippet (keep 140–160 characters)
@NAV    services                          ← highlights that item in the main navigation
@OUT    services/foo.html                 ← the logical page path (see URLs below)
@@                                        ← everything after this line is page content
```

### URLs — read this before renaming anything

The public URL of every page is **identical to the URL the live kneo.in already
uses**. That is deliberate: Google has those URLs indexed, and changing them would
reset the site's search rankings to zero on launch day.

The builder maps `@OUT` to a directory index automatically:

| `@OUT` | File written | Public URL |
|---|---|---|
| `index.html` | `index.html` | `/` |
| `about.html` | `about/index.html` | `/about/` |
| `services/foo.html` | `services/foo/index.html` | `/services/foo/` |
| `404.html` | `404.html` | `/404.html` |

You still write links as `{{BASE}}about.html` — the builder rewrites them to
`{{BASE}}about/`. Nothing in the page sources needs to know about this.

**Do not change an existing `@OUT` value** unless you intend to change a live URL.
If you must, add a 301 from the old URL to the new one in `.htaccess` first.

Valid `@NAV` values: `home`, `automation`, `mapp`, `products`, `services`, `industries`,
`company`, `contact`, `legal`, `none`.

### Change the navigation, footer or contact details
Edit `_source/partials/header.html` or `footer.html`, then rebuild. The change lands on
every page at once.

### Add a new page
1. Create a file in `_source/pages/` with the four metadata lines above.
2. Add a link to it in `header.html`, `footer.html` and `_source/pages/sitemap.html`.
3. Run `bash build.sh` — `sitemap.xml` updates automatically.

### Writing markup
Use `{{BASE}}` in front of every internal link — the build turns it into the correct
relative path (`""` at the root, `"../"` one level deep):

```html
<a href="{{BASE}}contact.html">Contact us</a>
```

## 4. Design system

Everything is driven by CSS custom properties at the top of `assets/css/main.css`.
Changing a brand colour is a one-line edit in each theme block.

| Token | Dark | Light |
|---|---|---|
| `--bg` | `#08080A` | `#FFFFFF` |
| `--surface` | `#111115` | `#FFFFFF` |
| `--text` | `#F4F4F7` | `#0B0B10` |
| `--accent` (text, icons, rules) | `#FF4B1F` | `#C7350A` |
| `--accent-fill` (filled buttons) | `#D93B0B` | `#C7350A` |

Two accent tokens exist deliberately: the bright accent is highly legible **as text on a dark
background**, but white text **on** that same bright orange fails contrast. `--accent-fill`
is the slightly deeper shade used for filled buttons so white button text stays accessible.
Every text/background pair on the site was measured at ≥4.5:1 in both themes.

**Type:** Plus Jakarta Sans (headings) · Inter (body) · JetBrains Mono (labels, numerals).

**Theme:** dark by default. The toggle in the header persists the choice in `localStorage`,
and an inline script in `<head>` applies it before first paint so there is no flash.

### Reusable building blocks
`.cardgrid` + `.cell` (bordered grid), `.card`, `.stats` + `.stat`, `.index-row`,
`.industry-tile`, `.timeline`, `.manifesto`, `.accordion`, `.tabs`, `.quote`,
`.article-card`, `.info-card`, `.callout`, `.chips`, `.table-wrap`, `.diagram`,
`.cta-band`, `.page-hero`, `.split`, `.pillars`, `.feature-list`.

Add `data-reveal` to any element for a scroll-in animation, or `data-reveal-group="0.08"`
on a container to stagger its children automatically.

## 5. Two assets you may want to replace

Both are optional — the site is complete and correct without them.

### Hero background video
The homepage hero currently uses a generated canvas animation (an industrial node network).
It needs no files, works offline and never fails to load.

To use real footage instead, drop an MP4 at:

```
assets/video/hero-factory.mp4
```

`main.js` probes the file first and only swaps it in **if it actually loads**, fading it over
the canvas. If the file is missing, corrupt, slow, or the visitor is on a small screen, in
data-saver mode, or has reduced-motion enabled, the canvas simply stays. Nothing 404s
visibly and nothing shifts layout.

Recommended: H.264 MP4, 1920×1080, 10–20 seconds, silent, under ~4 MB, showing KNEO's own
robotic cells, panels or shop floor.

### Social share image
`assets/img/og-cover.svg` is referenced by the Open Graph and Twitter card tags. **LinkedIn
and X do not render SVG share images.** Before promoting the site on social channels, export
that file as a 1200×630 PNG, save it as `assets/img/og-cover.png`, and update the two
`og:image` / `twitter:image` lines in `_source/partials/head.html`, then rebuild.

## 6. Brand logos

The **Industrial Automation** page has a tabbed platform grid — Controllers, Robotics,
Visualization, Engineering tools and Standards. Each entry is currently a **typographic
wordmark**: the brand name plus a line saying what we do with it.

### Why not real logos already

Siemens, Rockwell, Mitsubishi, Keyence, Ignition and the rest are **registered trademarks
owned by those companies**. Their logo files cannot simply be downloaded and republished —
most vendors publish brand guidelines that govern colour, spacing, minimum size and the
contexts in which their mark may appear, and several require written permission before a
third party displays their logo commercially.

Two safe routes:

1. **Partner / integrator programmes.** If KNEO is a registered partner with any of these
   vendors, the programme usually supplies an approved "Partner" badge and a media kit. That
   is the strongest option — the badge says more than the plain logo does.
2. **Official brand asset pages.** Most vendors publish a press or brand-resources page with
   downloadable SVGs and the terms of use. Check the terms cover third-party service
   providers before using them.

Until then, the wordmarks are deliberate — they read cleanly, carry no legal risk, and
mention what you actually do with each platform, which a plain logo does not.

### Adding a logo once you have the file

**Drop the file in and rebuild. There is no HTML to edit.**

1. Save the logo as SVG (preferred) or transparent PNG in `assets/img/logos/`,
   named after the tile slug, lower case — `bmw.svg`, `allen-bradley.svg`, `siemens.svg`.
2. Run `bash build.sh`.

The build looks for a file matching each tile's `data-logo` slug. Where one exists it
writes an `<img>` in place of the wordmark and uses the brand name as the alt text; where
none exists the wordmark stays. The build prints how many logos it found, so you can see at
a glance whether a filename was mistyped.

`assets/img/logos/README.txt` lists every available slug — 39 of them across the home page
and Industrial Automation.

The CSS renders every logo at 34px tall with the aspect ratio preserved, so a row of mixed
logos stays optically aligned. Marks are desaturated by default so a grid of clashing brand
colours still looks composed, returning to full colour on hover — remove the `filter` on
`.logo-tile__img` if a vendor's guidelines forbid recolouring. Image tiles and wordmark
tiles mix freely; they line up either way.

## 8. Deployment

Upload the repository root to the web root. `_source/`, `_tools/`, `build.sh` and
`start-server.cmd` are development files and can be left out of the upload if you prefer.
There is no server-side requirement.

kneo.in runs Apache, so **`.htaccess` is included and configured** — it handles HTTPS, the
canonical hostname, trailing slashes, the 404 page, compression and cache headers. Upload it
with the rest of the files. On Netlify, Vercel or Cloudflare Pages, `.htaccess` is ignored;
those platforms handle directory indexes and compression themselves, and only the 404 page
needs pointing at `/404.html`.

### Launch checklist

1. **Back up the current site first.** Especially `/blog/`.
2. **Keep `/blog/` in place.** This site does not contain the blog. It links to
   `kneo.in/blog/…`, which must keep working — do not delete that directory.
3. Upload everything, including `.htaccess`.
4. Spot-check the previously indexed URLs — they should all still resolve:
   `/about/` · `/services/` · `/mapp/` · `/industrial-automation/` · `/industries/` ·
   `/expertise/` · `/careers/` · `/contact/` · `/faq/` · `/products/pfmea/` ·
   `/products/auto-ballooning/` · `/products/mapp-vision/`
5. Resubmit `sitemap.xml` in Google Search Console so the ~25 brand-new pages get discovered.
6. Watch Search Console coverage for two weeks. Because no URL changed, rankings should hold.

If the site is ever served from a domain other than `https://kneo.in`, update `SITE_URL` at
the top of `build.sh` and the `canonical` / `og:url` lines in `_source/partials/head.html`,
then rebuild so `sitemap.xml` and the canonical tags point at the right host.

### Compression

The site is text-heavy and compresses roughly 4× (homepage 71 KB → 14 KB, CSS 61 KB → 12 KB,
JS 28 KB → 8 KB). `.htaccess` enables this via mod_deflate/mod_brotli where available.

### Contact form
The form currently opens the visitor's mail client with the enquiry pre-filled — it works
with zero backend. To post to a real endpoint instead, set the `action` attribute on the
form in `_source/pages/contact.html` to your form handler URL (Formspree, Netlify Forms, your
own API). `main.js` detects an `http` action and switches to a `fetch` POST with proper
success and error states automatically.

## 9. Quality checks performed

- **Links** — all 38 unique internal links resolve across all 39 pages; zero broken.
- **Responsive** — no horizontal overflow on any page at 360 / 768 / 1024 / 1440 px.
- **Headings** — exactly one `<h1>` per page; no skipped heading levels anywhere.
- **Contrast** — body text, leads, labels, nav, footer, buttons and chips all ≥4.5:1 in
  both themes.
- **SEO** — unique title and 140–160 character description per page, canonical URLs,
  Organization + FAQPage JSON-LD, semantic HTML, generated `sitemap.xml` and `robots.txt`.
- **No JavaScript** — every hidden-until-revealed state is scoped to `:root.js`, so with
  scripts disabled all content, including FAQ answers and tab panels, renders immediately.
- **Reduced motion** — `prefers-reduced-motion` disables animation, marquee and the canvas
  loop while keeping all content visible.
- **Resilience** — scroll reveals have a geometry sweep plus a last-resort timeout, so
  content cannot be stranded invisible by a background tab, an anchor jump or a failed
  IntersectionObserver.
